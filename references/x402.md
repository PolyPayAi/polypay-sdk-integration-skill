# x402 Agent Payments

Check the current contract at `https://polypay.ai/en/docs/x402-integration` before changing networks, schemes, or assets.

## Supported Flow

Use PolyPay x402 only for server-side paid HTTP resources. The current standard flow is `exact` with Circle USDC `transferWithAuthorization` on:

- Base: `eip155:8453`
- Ethereum: `eip155:1`
- Polygon: `eip155:137`
- Arbitrum: `eip155:42161`
- Optimism: `eip155:10`

Do not claim current standard support for BSC, Tron, Solana, TON, or BTC. They require another scheme or a future PolyPay extension.

AI Agent Payments requires an active subscription or Pay-as-you-go access. An inactive subscription freezes resource management and verify/settle runtime access without deleting saved resources.

## Implement the Resource

1. Create the Resource in the PolyPay Dashboard with its canonical public URL, HTTP method, price, network, Circle USDC contract, settlement wallet, description, and timeout.
2. Use `@polypay/sdk/x402` in server-side JavaScript/TypeScript or the PHP SDK `x402()` helper.
3. Keep the merchant API Key in server-only secret storage.
4. On an unpaid request, return HTTP 402 with the SDK-generated requirement.
5. Return the x402 v2 challenge in the `PAYMENT-REQUIRED` header.
6. On a request carrying `PAYMENT-SIGNATURE`, verify it and settle it through PolyPay.
7. Return protected content only when settlement reports success, and attach the SDK-provided `PAYMENT-RESPONSE` header.

The SDK emits x402 v2 by default. `protocolVersion: 1` and the legacy `X-PAYMENT` header exist only for an explicit, controlled migration and must not be used for new integrations.

The SDK and facilitator bind scheme, network, asset contract, payee, amount, resource URL, and HTTP method. They also validate the authorization window, nonce uniqueness, and EIP-712 signer.

## Handle Proxies and Retries

Configure the canonical external resource URL and method on the SDK helper. The SDK uses those values instead of a proxy-internal request URL; pass an explicit URL only for dynamically resolved PHP routes. The binding must exactly match the requirement and PolyPay Resource configuration.

Treat a nonce as single-use. The raw facilitator settlement returns `paymentId` and `replayed`; PolyPay SDK helpers map them to `fulfillmentKey` and `shouldFulfill`. `shouldFulfill=true` is limited to the request that wins the first confirmed payment-state transition, while concurrent and later replays receive false. This is not a substitute for merchant-side idempotency. For state-changing routes, atomically store the first business response under the unique key and return the stored response on retries; never run the side effect again merely because `paid=true`. Read-only routes may continue serving the protected representation when `paid=true`. Do not settle before verification succeeds, and do not reveal protected data on verification or settlement failure.

The merchant must configure and enable the matching x402 Resource in the Dashboard. PolyPay rejects disabled or missing resources. A raw standard facilitator request without explicit method/resource context is accepted only when its merchant, network, asset, amount, recipient, and enabled Resource resolve uniquely; otherwise use the PolyPay SDK canonical method/resource fields or unique payment terms.

A settle timeout is indeterminate. Retry the exact same signed payment proof so PolyPay can return or reconcile the nonce's existing settlement; do not generate a replacement authorization solely because the response timed out. SDK helpers reject unsupported schemes, networks, Circle USDC contracts, and EIP-3009 metadata before emitting a challenge.

## Required Tests

- No payment returns HTTP 402 and a valid requirement.
- Wrong resource, method, network, asset, amount, payee, signature, or time window fails.
- A valid Base, Ethereum, Polygon, Arbitrum, or Optimism USDC authorization settles once.
- A reused nonce cannot charge twice or fulfill twice.
- A proxy deployment matches the canonical public URL.

Use mocks and protocol test vectors for routine validation. Do not assume the normal order Sandbox simulates x402 settlement. Run a low-value production settlement smoke test only with explicit user authorization and an approved wallet.
